# BindPack 指标定义与可复现评测协议

> 融合依据：原位于根目录、现归档于 `archive/融合前原稿/` 的两版《新指标说明》、BindPack 实现和本地数据字段。定义核查日期：2026-10-16。2026-10-18 已按本文新增独立离线 evaluator、报告导出与自动补算；实现和使用方法见第 15 节。定义示例仍不是实验结果，本次指标开发没有重新运行检索或问答。

## 1. 最终采用什么指标

建议以 **EM/F1、文档 Recall@K、Full Chain Retrieval（FCR@K）**作为共同主评测，以 **Dependency-Closed Coverage（DCC@K）**作为有可信 gold dependency graph 的数据子集上的结构诊断。主表优先报告 K=5、10，附录补充 K=20、200。

| 指标 | 评测单位与问题 | 当前实现状态 | 论文定位 |
|---|---|---|---|
| EM、token F1 | 每个问题的最终答案是否匹配 gold answer/alias | 已实现，`qa_eval.py:19,55` | 标准问答指标 |
| 文档 Recall@K | 去重后的标注支持文档被最终排名前 K 位覆盖的比例 | 已实现，`retrieval_eval.py:24` | 标准检索指标 |
| FCR@K | 前 K 位是否包含完整标注支持文档集合 | 已实现逐题与宏平均，可从已有排名离线补算 | 已有完整性指标，不作为新贡献 |
| DCC@K | 多少 gold evidence nodes 的自身和所有前置节点同时被覆盖 | 已实现独立 MuSiQue gold DAG 构建器和离线 evaluator；其他数据集缺少可信图时为 null | 结构评测视角，不声称首创 |
| NodeCov@K、ClosureGap@K | 不考虑依赖的节点覆盖，以及其中未转化成闭合覆盖的部分 | 已实现，与 DCC 同时导出 | 诊断量，不另包装成创新指标 |
| JSR_EM@K | FCR 成功且同一上下文条件下严格 EM 成功的查询比例 | 未实现，可在口径固定后离线计算 | 可选联合诊断，需明确与引用论文的答案正确判定差异 |

统一使用 **DCC**，不再混用 ECC、DECC、DCR。旧版 DCR 若只是“所有必需文档都检索到”，与 FCR 等价；不另立名称重复申报创新。CatRAG 正式版 §4.3 已定义 FCR 和 JSR，见 [Findings ACL 2026 论文，第 6 页](https://aclanthology.org/2026.findings-acl.290.pdf)。其 JSR 使用答案正确条件，不能未经实现核对就等同于严格 EM。

这些指标是并列观察维度，**不是 Recall → FCR → DCC 的串行算法**。特别是 FCR 二值化并不会向 DCC 提供输入。

## 2. 排名、文档身份与 K 的统一口径

对问题 q，令最终有序结果为 L(q)=[d₁,…,dₘ]，取其前 min(K,m) 个排名位置，再取集合得到 R_K(q)。K 是**原始 passage/document 的排名位置数**，不是 token 数、三元组数、推理节点数、包数或 LLM 调用数。

当前代码以完整字符串 `title + "\n" + text` 精确比较文档，没有采用 title-only、答案字符串命中或语义相似匹配。HotpotQA 句子拼接为 `"".join(sentences)`，2Wiki 为 `" ".join(sentences)`；差一个空格也可能使同一篇文章失配，见 `scripts/eval_utils.py:66`。所有 baseline 应使用同一 canonical passage ID/文本映射，并保留映射版本；不能一方按标题评测，另一方按完整段落评测。

现有 Recall 先切片再取集合，重复文档会占用 K 个排名位置但不重复计分。正式实验要求检索排名无重复并记录重复率；不能在评测时只替某个方法去重、回填新文档。一个文档支持多个 gold nodes 时，文档 Recall 只记一个文档，DCC 可以覆盖多个节点，二者分母不同。

| 当前参数或字段 | 实际含义 | 不能误解为 |
|---|---|---|
| `retrieval_top_k`，默认 200 | 检索返回的最终排名长度上限 | reader 实际读入的文档数 |
| `result_top_k`，默认 10 | JSON 中 `docs`、`doc_scores` 的展示截断 | 整个系统只检索了 10 个文档 |
| `candidate_output_top_k`，默认 200 | `candidate_docs` 保存 `solution.docs` 的较长前缀 | Route 原始候选并集、所有检索尝试或包列表 |
| `qa_top_k`，默认 5 | QA reader 实际使用 `query_solution.docs` 的前缀 | 同一次答案可用于任意 K 的联合评测 |
| `gold_document_ranks` | gold 文档在完整 `solution.docs` 中的最早排名，未出现为 null | 在整个 corpus 中的 oracle 排名 |

来源：`scripts/eval_dataset.py:460`、`evaluation/result_export.py:4`、`utils/misc_utils.py:46`、`core/base.py:590`。离线重算 R@20 不能只读默认 10 条的 `docs`；应使用足够长的 `candidate_docs` 或导出的 gold ranks。输出长度不足 K 时必须报告实际长度与不足比例，不能把 Recall@200 描述为“保证返回 200 条”的实验。Pack 实际改变顺序后还会用递减的合成排名分值重新赋值 `doc_scores`（`evidence_dag_package.py:333`）；这些分数不能当作跨方法可比的相关性概率或置信度。

## 3. 文档 Recall@K：与现有实现一致

令 S_q 是去重后的 gold supporting document 集合。对 S_q 非空的问题：

\[
\operatorname{Recall}(q,K)=\frac{|R_K(q)\cap S_q|}{|S_q|}.
\]

数据集结果是**按问题宏平均**：

\[
\operatorname{Recall@K}=\frac{1}{|Q_{doc}|}\sum_{q\in Q_{doc}}\operatorname{Recall}(q,K).
\]

这与“先汇总所有问题命中文档数再除以所有 gold 文档数”的微平均不同。主表只用宏平均；若补充微平均，显式标为 Micro-Recall，并写清分母。

当前代码对空 gold 集合给 0.0，并把它纳入整体平均；检索列表为空而 gold 非空时也是 0。`retrieval_eval.py:42` 使用 `zip`，未自行检查两个输入列表等长；整体 gold 列表为空时仍会除零。正式运行应在调用前验证输入对齐和非空。缺少证据标注的问题不是检索失败，应预先列入“不可评文档指标”名单并报告标注覆盖率，不能运行后按结果删题；若要与原程序数值复现，另保留含空 gold=0 的兼容结果。

`engine.py:758` 的整体 K 列表为 1、2、5、10、20、30、50、100、150、200；`result_export.py:11` 的逐题 Recall 仅含 1、2、5、10、20、200；`stratified_eval.py:105` 的默认 K 又不同。论文表格应从逐题统一重算并按同一 K 集合汇总，不能把缺失字段默认为 0。

## 4. FCR@K：严格的标注集合完整性

对非空 S_q：

\[
\operatorname{FCR}(q,K)=\mathbf1[S_q\subseteq R_K(q)],\qquad
\operatorname{FCR@K}=\frac{1}{|Q_{doc}|}\sum_{q\in Q_{doc}}\operatorname{FCR}(q,K).
\]

FCR 的分子是“完整覆盖的问题数”，分母是有有效支持文档标签的问题数，**不是检索文档数**。它在每题上等价于 Recall(q,K)=1，但宏平均 FCR 不能从宏平均 Recall 还原。

当前 `all_gold_in_top5` 和 `all_gold_in_top10` 正是非空 gold 条件下的逐题 FCR 判定，可直接平均得到 FCR@5、FCR@10；其他 K 可根据 gold ranks 判定 `all(rank is not None and rank <= K)`，前提是排名导出范围足够，见 `result_export.py:21`。不把空集合的数学“真空为真”算作成功。

FCR 检查标注支持文档是否一起出现，**不检查依赖边顺序、实体绑定正确性、句子蕴含或 reader 是否真的利用了证据**。若 S_q 有 4 篇独立必需文档，则 FCR@2 必为 0；这种预算可达性需要在分层结果中解释。

对于只提供一个 gold set 的数据集，主协议固定使用该集合。只有数据集或独立标注确实给出了多组充分证据时，才可另报 `AnySet-FCR`：存在至少一个充分证据集合被完整覆盖。不把多个 alternative sets 的并集误当成全都必需，也不把“至少一组”悄悄替代标准 FCR。

## 5. DCC@K：依赖闭合的部分覆盖

### 5.1 Gold graph 和节点覆盖

构造独立于所有被评方法的 gold DAG：G_q*=(V_q,E_q)，边 u→v 表示完成 v 必需先有 u 的信息。V_q 只包含需要外部证据的节点；纯计算/比较终结节点不占证据分母。若从带计算节点的图投影为证据图，必须保留穿过这些节点的传递依赖，而不是简单删边。所有 predecessor 默认是 **AND 依赖**，不能把任选其一的 OR 分支强行写成 AND。

在最常见的“一个节点由任一合法支持文档单独支撑”的情况下，令 S_v 为该节点的 alternative supporting document set：

\[
c_v(q,K)=\mathbf1[R_K(q)\cap S_v\neq\varnothing].
\]

注意 S_v 的这个定义是 OR。若一个节点必须同时读两篇文档，不能继续使用上述非空交集判定，应定义预先标注的充分证据束族 B_v：

\[
c_v(q,K)=\mathbf1[\exists B\in\mathcal B_v:B\subseteq R_K(q)].
\]

单文档 alternatives 是每个 B 都为单元素集合的特例。第一版建议优先使用 MuSiQue 原生单段落节点，暂不引入未经标注的复杂 bundles。

### 5.2 闭合覆盖与聚合

令 Anc(v) 为 gold DAG 中 v 的全部祖先，定义：

\[
\widetilde c_v(q,K)=c_v(q,K)\prod_{u\in Anc(v)}c_u(q,K).
\]

根节点祖先集合为空，空乘积为 1。则：

\[
\boxed{\operatorname{DCC}(q,K)=\frac{1}{|V_q|}\sum_{v\in V_q}\widetilde c_v(q,K)}
\]

\[
\operatorname{DCC@K}=\frac{1}{|Q_{dag}|}\sum_{q\in Q_{dag}}\operatorname{DCC}(q,K).
\]

这是**先逐题按节点归一化，再按问题宏平均**。节点多的问题不额外获得权重。附录若报微平均，使用所有 closed nodes 总数除以所有节点总数，并明确标签 `Micro-DCC`。|V_q|=0、缺证据映射、非 DAG 或依赖解析失败时标为不可评，报告数量/原因；不能记为 DCC=1，不能依据检索结果修补 gold graph。

DCC 只衡量“文档覆盖符合独立 gold dependency topology 的程度”。它不证明方法生成了正确计划，不检查检索时间顺序，也不证明实际推理忠实性。即使一个 baseline 没有 planner，只要其输出能映射到相同的原始文档，仍能公平计算 DCC。

### 5.3 例子与数学边界

以下仅是定义示例，不是实验结果。线性图 s₁→s₂→s₃，每个节点恰好对应一篇不同的必需文档：

| 命中的节点 | 文档 Recall | FCR | NodeCov | DCC |
|---|---:|---:|---:|---:|
| s₁,s₂,s₃ | 1 | 1 | 1 | 1 |
| s₁,s₂ | 2/3 | 0 | 2/3 | 2/3 |
| s₁,s₃ | 2/3 | 0 | 2/3 | 1/3 |
| s₂,s₃ | 2/3 | 0 | 2/3 | 0 |

在线性图上 DCC 是从根开始连续覆盖的最长前缀长度除以总节点数；在 DAG 上应按每个节点的全部祖先计算，不能改成一条任意最长路径。对于菱形 s₁→{s₂,s₃}→s₄，命中 s₁,s₂,s₄ 而缺 s₃ 时，DCC=2/4。

定义节点覆盖率：

\[
\operatorname{NodeCov}(q,K)=\frac1{|V_q|}\sum_v c_v(q,K),\qquad
\operatorname{ClosureGap}(q,K)=\operatorname{NodeCov}(q,K)-\operatorname{DCC}(q,K).
\]

因此总有 0≤DCC≤NodeCov≤1，ClosureGap 非负。**一般不能直接用文档 Recall−DCC**：只有节点与文档一一对应、每题 gold 集合完全一致时 NodeCov 才等于文档 Recall。在这一特例下还满足 FCR≤DCC≤Recall。多节点复用一个文档、节点有 alternatives 或多文档 bundles 时，不能照搬这一不等式。

没有依赖边时 DCC=NodeCov，属于合理的负对照。固定图与匹配规则下，K 增大时每题 DCC 不下降。若声称 DCC 提供额外信息，必须报告与 Recall、NodeCov 的相关性、同 Recall/NodeCov 条件下的 DCC 差异和实际排序是否变化；高度重合就降低其贡献定位，不能为体现创新随意改定义。

若确有多个合法 gold graphs，可在预先固定的图族上另报 `AnyGraph-DCC=max_G DCC(q,K;G)`；应同时说明图数、各图节点数和标注来源，避免借更小或更容易的图抬分。主结果优先采用 dataset-native 的单一规范图。

## 6. Gold graph 从哪里来：按数据集决策

| 数据集 | 当前文档 gold 来源 | DCC 的可行性与边界 |
|---|---|---|
| MuSiQue | `paragraphs[*].is_supporting`，文档为 title+正文 | **首选**。用 `question_decomposition` 中 `#i` 引用建立边；按 decomposition 的位置解析 #i，不使用 step 的全局 `id` 当引用序号；`paragraph_support_idx` 映射 `paragraphs[*].idx` |
| 2WikiMultiHopQA | `supporting_facts` 标题映射 `context` | 有 `evidences/evidences_id` 但不能直接把排列视作串行链。需独立验证 triple/entity 到 supporting passage 的映射、边方向、并行/比较结构；验证通过前只报 Recall/FCR |
| HotpotQA | `supporting_facts` 标题映射 `context` | 没有 MuSiQue 式显式 decomposition。`bridge/comparison` 不是完整 gold DAG；主表报 Recall/FCR，只有经独立标注验证的结构子集再报 DCC |
| NQ、PopQA | `contexts` 或 `paragraphs` 的支持标记 | 适合作单跳保真/退化检查，通常没有额外依赖诊断价值；不为凑齐列而伪造多跳图 |

特别注意当前 gold 提取的宽松回退：NQ 风格 `contexts` 若没有任一 `is_supporting=True`，会把全部 contexts 作为 gold；paragraph 数据只排除显式 `is_supporting=False`，未标记的项也会入 gold，见 `eval_utils.py:85`。正式报告应披露这种标签语义，不能一概声称所有 gold 都是人工最小充分证据。完整覆盖所有可替代支持文档的 FCR 在单跳数据上也可能过严，因此 NQ/PopQA 主要看 EM/F1 与标准文档 Recall，FCR 仅作带注释的补充。

已做的本地**只读字段审计**：原 `Data/hipporag2_datasets/musique.json` 共 1000 题，2/3/4 节点分别 518/316/166；逐题检查 #i 指向更早步骤、支持索引存在、支持段落标志为真、规范字符串能在 `musique_corpus.json` 找到，以上检查未发现错误；每题 decomposition 支持文档没有重复。2026-10-18 新构建器对本轮 `/root/datasets/musique.json` 的 1000 题也全部通过原生标签与精确 corpus 映射验证。evaluator 已实现，但格式通过不证明依赖标注语义完全正确；DCC 实验数值仍须由实际完成的检索结果计算，不能预填。

Gold DAG 构建器必须与 BindPack planner 分开。不得使用本方法生成的 plan、binding、winning branch 或 package eligibility 定义 gold；不得用最终 gold answer 再去检索、重排或修补候选。离线映射可以读取数据集监督字段，但评测结果只能在检索结束后加入。

## 7. 当前代码的 gold 使用边界：必须如实披露

不能直接写“gold information never enters retrieval planning”。这句只能限定为某一导出函数或 Pack 局部，不适用于整个当前实验入口。

1. **Gold 文档评测**：`engine.py:756` 在检索结束后调用 Recall；`result_export.py:4` 在导出时加入 gold docs、ranks、命中标志。Pack 的局部 trace 为 `gold_labels_used=False`，不等于系统从未使用任何监督。
2. **Oracle hop 条件**：`eval_utils.py:20` 从 MuSiQue 的 gold decomposition 长度得到每题 2/3/4-hop；`eval_dataset.py:104` 显式标记 `per_question_oracle`，在第 284 行传入 `set_query_hop_overrides`；`engine.py:364` 要求每题有显式 hop 数。这个数会影响检索与分解预算，因此是测试时额外信息，不只是分层标签。HotpotQA/2Wiki 的 2、NQ/PopQA 的 1 是数据集先验，不能称为实际逐题串行跳数。
3. **Corpus 补入 gold**：`eval_dataset.py:140` 可把缺失 gold docs 补进索引语料，参数在第 450 行默认开启。固定完整 benchmark corpus 中只做一致性检查最好；若发生补入，应记录数量、文本与最终 corpus hash，并把完全相同的冻结语料给所有 baseline，不能只提升 BindPack 的可检索上界。截断语料后补入 gold 更不能当作自然完整语料实验。
4. **sample_only 语料**：仅从所选样本构造的小语料可用于 smoke test，不能和指定完整 benchmark corpus 的 baseline 论文值并排比较。这里的 full 仍是给定 benchmark corpus，不自动等于全维基。

公平比较至少分成明确条件：A）所有方法只使用问题和同一公开数据集先验；B）oracle-hop 辅助条件，所有支持预算控制的方法获得相同 hop 信息。**当前代码直接支持 B 的 MuSiQue 设置；A 需要另加不读取测试标签的 hop/预算策略或固定策略再运行，不能靠改实验名称实现。** 若 baseline 本身不使用 hop 输入，也必须披露 BindPack 的侧信息差异，并通过固定预算/额外控制实验量化影响。

## 8. 与真实 Pack 实现相匹配的评测重点

`selection/evidence_dag_package.py:181` 的 `_closed_coverage` 在**预测 plan 和经过来源检查的候选 proofs**上计算闭合；它是方法内部目标，不是 gold DCC。`_package_sets` 枚举可支持的祖先闭合节点子集；`_optimize_prefix` 按“完整叶节点数、闭合节点数、较少新加入文档、原排名代价”做字典序比较，并非实现了一个 gold-DCC 最大化器。

该实现先优化 Top5 且保留前 2，再优化 Top10 且固定已优化 Top5；并检查 Top200 集合、全部文档集合和唯一性不变，见第 207、258、302 行。因此：

- 对**同一输入排名、同一候选集合，仅切换 DAG package reranker**的局部控制，R@1/R@2 和 R@200/FCR@200 应保持不变，变化重点是 Top5/Top10 的共同保留质量；不能把 R@200 上升归因于这个局部重排。这里不包含基础 greedy 或最终 veto 的改动，完整 Pack 不共享全部这些不变量。
- 需要同时看 R@5/10、FCR@5/10、gold-DCC@5/10；另外报告包优化前后的逐题变化、候选可达上界及触发率。内部闭合增加不保证 gold DCC 或答案正确率增加。
- `entailment_guaranteed=False` 是当前 trace 的明确边界。来源检查、结构闭合与语义正确不是同一件事；某篇证据在原文出现，不足以证明跨文档实体绑定和关系都正确。
- 完整端到端消融还会受 Plan、prune、独立 veto 等影响；若比较不同运行的最终输出，不能用上述 Pack 局部不变量解释所有差异。

Route/Plan/Pack 可以分别关联候选可达性、依赖暴露和预算内集合选择，但不能事先规定“Route 只影响 Recall、Plan 只影响 DCC、Pack 一定显著提高 FCR”。它们都可能影响多个指标，结论由配对结果决定。

## 9. EM/F1 和联合成功：答案条件必须对齐

当前 EM 先小写、删 ASCII 标点、删英文冠词 a/an/the、合并空白，再与任一 gold alias 比较取最大；token F1 使用相同规范化后的词袋重合，按 alias 取最大，最后按问题宏平均，见 `qa_eval.py:38,71` 和 `utils/eval_utils.py:4`。这不是语义裁判或 substring correctness。当前 F1 对两个空规范化字符串也返回 0，而 EM 会相等为 1；空 alias 列表还会触发 `np.max([])` 错误。正式运行应预先验证有效答案标签，失败/空预测在有正常非空 gold 的题上计 0，并报告失败率。

若加入严格联合指标，定义：

\[
\operatorname{JSR_{EM}@K}=\frac1{|Q_{joint}|}\sum_q\operatorname{FCR}(q,K)\operatorname{EM}(q;R_K).
\]

必须让 EM 的答案由同一个 Top-K 或同一个明确 token budget 的上下文生成；默认 `qa_top_k=5` 的一次生成不能同时冒充 JSR_EM@5、@10、@20。若仅观察 `FCR@10 × EM(reader@5)`，须完整标为 `FCR@10 ∩ EM(reader@5)`，不简称 JSR@10。读取已有输出时先检查 `gold_answers` 是否实际存在；纯 retrieve 输出不保证填充 QA gold，必要时按 sample_id 从冻结原数据重建。

报告中也可以列出四格诊断：FCR 成功/失败 × EM 成功/失败。完整证据且答案错只能说明 reader/语义等环节仍可能失败；证据不完整而答案对也不能单凭这一点判定模型幻觉，可能来自参数记忆、标注遗漏或替代证据。

## 10. Baseline 公平比较的具体要求

所有方法统一问题 ID、split、冻结 corpus、chunk 规则、原始文档 ID、支持文档标签、gold DAG、reader 模型/提示/温度、上下文截断与 K。检索返回越长，不应自动拥有更多 reader 上下文；除了固定 passage K，建议补充固定 token budget 对照，量化段落长度差异。

外部方法若输出 summary、triples、subgraphs 或生成文本，应先明确是否能追溯到实际取用的原始 passages。能追溯才可按统一去重文档前缀评测，并披露 provenance 展开后预算；不能将一个 summary 节点计作一个 passage，却给它背后的全部源文档免费记分。没有可靠 provenance 时，其答案 EM/F1 仍可比较，文档 Recall/FCR/DCC 标为 N/A，另列端到端表。CatRAG 正式版第 7 页表 2/4 对不直接产生 passage retrieval 的方法也作了区分，见 [原文](https://aclanthology.org/2026.findings-acl.290.pdf)。

其他论文报告值仅作为带模型/数据条件的参考；不能直接填入本地统一评测表，尤其不能把 GPT-4o-mini、不同 embedding、不同 reader、oracle-hop 与本地 qwen/NV-Embed 条件混成一个胜负排名。DCC 需要给所有方法重新算，不能只对 BindPack 算后用来声称领先。

## 12. 实现与后续分析清单

1. 冻结 dataset、corpus 和 sample manifest，保存文件 SHA-256、split、sample IDs、随机 seed、代码 commit、模型/reader/prompt/config 与 oracle 信息。
2. 对每个 baseline 导出统一的最终原始文档 ID 排名（至少 max K）、答案、reader 实际上下文与 token budget；验证无重复和逐题对齐。
3. 独立构建 MuSiQue gold DAG；验证引用范围、无环性、节点→段落 idx→canonical corpus ID、全部支持节点映射、标注覆盖率；人工抽检并冻结标签文件。
4. 统一离线计算 Recall、FCR、NodeCov、DCC、ClosureGap 与可选 JSR_EM，逐题保存分子/分母、validity、gold graph version、闭合节点和缺失祖先；不能只输出总平均。
5. 校验：完整 gold 时 FCR=1；链根缺失时下游不计闭合；独立根图 DCC=NodeCov；K 增大不降；文档重复不多得分；同一文档覆盖多节点时不混文档/节点分母；非法/空图为不可评；DAG package reranker 局部 Top2/Top200 不变量成立。
6. 做同题配对汇总、置信区间、预算/深度分层、相关性与错误案例；缺标注的 DCC 子集同时列出同子集的 Recall/FCR，避免比较不同 N。

第 1–5 项所需的指标构建、身份校验、逐题输出与数学回归已落地；人工语义抽检、各方法完整结果及第 6 项统计分析仍需以实际产物为准。JSR_EM、bootstrap、置信区间和相关性分析不在本轮实现范围内，不能填任何预期提升数字。

## 13. 论文表格与结论模板

主表建议把宽表分为两张：共同质量表列 `Method | EM | F1 | R@5 | R@10 | FCR@5 | FCR@10 | reader budget`；MuSiQue 结构表列 `Method | N_DAG | NodeCov@10 | DCC@5 | DCC@10 | ClosureGap@10`。两表均列 oracle-hop 条件与 provenance 不适用标记，避免堆砌大量同义指标。

关键分析优先使用：① 相同候选排名下 Pack 前后的配对变化；② 按 NodeCov/Recall 分箱的 DCC；③ 预算 K/上下文 tokens 曲线；④ 随 gold DAG 深度变化的 FCR/DCC；⑤ 完整证据与答案正确性的四格诊断。Recall–DCC 散点只能展示实际结果，且在分母不同情况下同时标出 NodeCov，不能预画 BindPack 位于其他方法之上的图。

可使用的中性英文定义：

> We report document Recall and Full Chain Retrieval to distinguish partial evidence recovery from complete annotated evidence recovery. On examples with independently constructed gold dependency graphs, Dependency-Closed Coverage measures the fraction of evidence nodes whose supporting evidence and all required ancestors are covered. We evaluate all methods using the same evidence mapping, context budgets, and disclosed hop-information conditions.

只有结果支持时，才进一步写“在相近 Recall 下具有更高 DCC”或“Pack 在固定候选与上下文预算下提高证据共同保留”。即使出现正向结果，也应将因果范围限定在相应受控消融。

## 15. 已实现的离线报告（2026-10-18）

实现分别位于 `evaluation/gold_graph.py`（独立标签）、`evaluation/structural_metrics.py`（逐题与宏平均）和 `evaluation/metric_report.py`（来源校验及持久化），均在 `src/bindpack/` 下。默认 K 为 5、10、20、200；可通过 CLI `--ks` 指定。指标只读取最终排名与冻结标签，不改变 Route、Plan、Pack、reader、LLM 缓存或索引。

每个结果目录新增：

- `report.json`：EM/F1、Recall、FCR、DCC、NodeCov、ClosureGap 的汇总，0–1 原值及百分数、每列有效分母、不可评原因、输入和 evaluator 摘要。
- `metrics_details.json`：逐题指标、gold 图、闭合节点、缺失祖先、文档命中、排名不足与重复诊断。汇总报告记录该文件的摘要。

HotpotQA、2Wiki 的 `DCC@K`、`NodeCov@K`、`ClosureGap@K` 为 `null`，`graph_n=0`，原因为 `dataset_has_no_verified_gold_dependency_graph`，不能改填 0 或从预测 plan 构造标签。MuSiQue 使用位置引用与原生支持段落计算，并在相同有效图子集上另报 Recall/FCR。

已有实验不用重跑；在项目根目录执行：

```bash
# 补算指定已完成结果，不调用模型
python scripts/report_metrics.py \
  --case outputs/3multi_hop_datasets_results_10_5/cases/hotpotqa/full

# 补算当前四组及 HippoRAG；没有 validated.ok 的目录跳过
python scripts/report_metrics.py \
  --cases-root outputs/3multi_hop_datasets_results_10_5/cases
```

CLI 默认核对 `validated.ok` 与原结果 SHA、case 协议、冻结 sample manifest、问题顺序、数据与 corpus 摘要；遇到身份不匹配拒绝输出。报告采用原子写入与目录锁，并支持重复执行。原 `result.json`、`validated.ok` 和检索协议不改写。已有导出缺少足够排名信息时标为不可评，不把未保存的尾部当成检索失败。

新评测入口保存结果后会自动写报告；主 runner 也在每组校验后生成报告，覆盖外部 HippoRAG。报告写入失败单独记录 `report_error.json`，已完成的检索结果保留，可离线重试。对已经加载旧代码的当前批次，单独的 CPU watcher 在每个 `validated.ok` 出现后补算：

```bash
python -u scripts/report_metrics.py \
  --cases-root outputs/3multi_hop_datasets_results_10_5/cases \
  --watch --runner-pid <原实验父进程PID> \
  --batch-dir outputs/3multi_hop_datasets_results_10_5/metadata/stage_ablations_qwen3_reuse
```

它不启动、停止或重跑评测，原实验结束后完成最后一次扫描并退出。本轮已完成的 HotpotQA Full（1000 题）离线 FCR@5/10/20/200 分别为 87.9%/93.4%/96.0%/99.4%，数值来源保存在该组 `report.json`；DCC 不可评。

当前批次原源码协议继续保留。为了仅新增报告而仍可断点继续，`configs/metrics_reporting_update.json` 精确记录已核对的两个保存钩子文件变更和五个报告文件新增；其他代码、模型、方法参数及输入必须完全相同。恢复时报告更新另记 `reporting_protocol.json`，不覆盖原检索协议。新的实验正常冻结当前完整源码；此规则不允许把算法变更当作指标更新继续旧结果。
