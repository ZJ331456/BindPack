# BindPack：Route、Plan/Bind、Pack 与四组实验

本文描述当前源码和实验入口。公开接口只有 `from bindpack import BindPack, BindPackConfig`，使用 `BindPack(config=cfg)`；配置按候选池、Route、Plan、Pack 分组。算法实现只有一份，不保留旧模块路径、历史配置 flags 或旧实验入口。

## 1. 方法职责与实际产物

| 阶段 | 方法名称 | 解决的问题 | 产物 |
| --- | --- | --- | --- |
| Route | Adaptive Evidence Route Construction | 从哪里发现可能支持复杂问题的材料？ | 初始候选、静态/路径条件子问题、图传播融合排名和轻量路径 |
| Plan/Bind | Source-Bound Dependency Planning and Execution | 哪个检索依赖哪个中间答案，答案由哪个来源支持？ | 可执行 DAG、按层绑定、单一保留分支、引用 proof 与失败诊断 |
| Pack | Dependency-Aware Evidence Packaging | 如何在有限前缀内联合选择相互依赖的证据？ | 覆盖/冗余感知前缀、有效来源支持的祖先闭合包提升、最终来源保护与审核 |

Plan/Bind 与 Pack 可以作为论文主要方法，Route 作为候选发现支撑；这属于叙事组织，不等于已经证明新颖性或效果。IDF、缓存、线程池、JSON 解析和每条关系规则不应各自列作创新。

必须区分三组概念：

1. QD/PCQD 生成检索方向，属于 Route；带 `${s1.answer}` 的依赖 DAG 属于 Plan，两者不是同一次分解。
2. Path-set 操作 `seed → passage` 或 `seed → bridge → passage`，属于 Route；读取获胜绑定分支和传递祖先的 DAG package 属于 Pack。
3. Source-bound 主要发生在依赖执行和来源核验阶段。Planner 的 LLM 输入是原问题、结构提示与预算，不读取候选原文；不能称为“根据证据原文规划 DAG”。PCQD 的 grounding 也不能自动转移为 planner grounding。

当前方法是有限计划、局部来源规则与受保护前缀的近似选择。它不保证所有返回 passage 均被验证，不保证任意 Top-K 都完整闭合，也不提供一般语义蕴含证明。

## 2. 源码结构与执行链

```text

│   └── defaults.json          默认方法数值的唯一来源
├── config.py                  BindPackConfig 组合与四组实验校验
├── retrieval/engine.py        在线检索、Route 窗口调度、结果导出
├── pipeline.py                EvidencePipeline：共享候选池与 Plan/Pack 编排
├── stages/
│   ├── route/                 RouteStage
│   │   ├── query_seed_prior.py         QuerySeedPrior
│   │   ├── bridge_expansion.py         BridgeExpansion
│   │   ├── iterative_refinement.py       IterativeRefinement
│   │   ├── route_refinement.py      QD / PCQD Route Refinement
│   │   ├── path_set_consolidation.py   PathSet Consolidation
│   │   └── baseline.py        w/o Route 固定候选适配器
│   ├── plan/                  PlanStage
│   │   ├── question_structure.py
│   │   ├── dependency_planner.py
│   │   ├── plan_canonicalizer.py / plan_validator.py / validation.py
│   │   ├── dependency_executor.py / answer_binder.py
│   │   └── source_verifier.py / answer_validation.py / relation_guard.py
│   └── pack/                  PackStage
│       ├── evidence_scorer.py / coverage_selector.py
│       ├── redundancy_controller.py / dag_package_selector.py
│       ├── dependency_closure.py / proof_support.py / proof_scope.py
│       └── verification/      最终 support guard 与 semantic veto
├── utils/evidence.py          文本、局部排名和分支匹配辅助函数
├── index/                     OpenIE、图索引、IDF 与 bridge cache
├── core/                      公共模型初始化、dense retrieval 与 QA
├── storage/                   向量与文本存储
└── evaluation/                检索与 QA 指标
```

`EvidencePipeline` 显式组合 `PlanStage` 和 `PackStage`；Plan 再组合 planner、executor、verifier，Pack 组合 scorer、coverage selector 和 DAG selector。没有历史多层 EvidenceRetrieval/Mixin 继承链。Route 的内部组件围绕图索引与查询状态协作。

```text
离线 corpus → OpenIE / embedding / 图索引 → IDF 与 bridge cache

问题 q + 显式 hop 提示
  → query-to-fact scores → fact filter
  → 有 facts：种子 / bridges → PPR → 有限第二轮 → 初始 base
    无 facts：dense retrieval → 初始 base
  → 静态 QD → 子问题 DPR 累积 → 子问题集合引导的 PPR track
  → 初始 base 来源片段 + seeds/bridges → PCQD hints → PCQD 子问题
  │
  ├─ EvidencePipeline.process_window
  │    初始 base Top80 + 静态/PCQD 子问题的独立 DPR 候选
  │      → Plan：问题结构控制 → DAG 规划/校验/剪枝
  │      → 按拓扑层：绑定 → DPR → 来源核验 → 单分支保留
  │      → 子目标候选保留与共享 pool 裁剪
  │
  └─ 检索主循环
       有 facts：base/static/PCQD track fusion → path-set
       无 facts：dense fallback 主排名
         → Pack：base/goal 分数 + coverage/redundancy greedy
         → 有限 Top5/Top10 DAG package
         → 真实物理来源 ID 对齐 → final support/semantic veto
         → 最终排名 → 可选 reader QA → 评测/导出
```

不能把它画成“最终 path-set pool → planner → 只有 verified passages → Top-K”的单线。Plan 使用初始 base 和独立子问题 DPR 候选，在最终 track fusion/path-set 之前运行；绑定后的新 DPR 还会引入候选。Pack 最后读取融合主排名和同一份 Plan state。

无 facts 时并非整个系统退回纯 DPR：Plan 依赖检索与 Pack 仍可运行，但缺少常规图 track fusion/path-set。失败、无 proof、无有效 PCQD 与预算耗尽都应按 trace 报告，不能默认每个模块对每题都激活。

## 3. Route：发现、细化与路径整合

### 3.1 QuerySeedPrior 与 BridgeExpansion

从通过 fact filter 的三元组提取实体。query/entity embedding 内积经 IDF 和 hub penalty 调整；hop 决定 softmax temperature 与 PPR damping。该分布还与 fact relevance/文档关联度先验按 `0.5/0.5` 混合，因此完整说明不能只有“similarity × IDF × hub penalty”。

Bridge 候选来自种子的图邻居，必须出现在 first-hop dense passages 对应实体集合中；有 query/entity embedding 时再按语义阈值过滤。邻居以 `IDF/(1+degree)` 排序。缺少 embedding 时不一定拒绝邻居，因此不能声称所有 bridge 均已通过语义验证。

### 3.2 IterativeRefinement、QD 与 PCQD

第二轮仅从首轮 Top1 passage 暴露的实体中选新 seeds，排除原 seeds 和无 embedding 实体，按 IDF 取 Top5，做一次 PPR 并按原系数融合；不是任意多轮 agent 搜索。

静态 QD 先对子问题做 DPR，汇总文档、实体和局部权重，再为整个子问题集合运行一个 PPR track。不是每个子问题分别运行完整 PPR；旧诊断名中的 `sub_query_ppr_used` 不代表实际逐题 PPR 次数。

PCQD 根据初始 base 文档、seeds 和 bridges 构造带来源片段的 hints，检查实体与引用 hint 的支持关系。它依赖可用静态 track，包含无 hints/无有效结果时的回退与权重归一化。默认 `0.4/0.2/0.4` 仅是三路有效时的配置，并非每题实际权重。

### 3.3 PathSet Consolidation

在 Top80 主排名文档中构造直接/桥接轻量路径，对 relevance、connectivity、consistency、completeness 四项归一化加权；按路径质量与新增 seed 覆盖贪心选至多 12 条，同一 passage 不重复。路径分数以原有 `0.7 × 主排名 + 0.3 × path score` 回写。Completeness 是 seed 覆盖代理量，不是 gold chain completeness 或逻辑验证。

## 4. Plan/Bind：依赖计划与来源绑定

### 4.1 QuestionStructureController 与 DependencyPlanner

问题结构控制器只读取问题文本，保守识别明确的并行比较/属性结构；含糊的 `and` 不直接触发扩容。明确并行结构的总节点和依赖深度分开限制，默认 6/4；简单链的节点容量仍受 hop 提示限制。两类结构保留原 Full 各自的 prompt/校验策略；它们是同一个 planner 的内部结构策略，不是历史兼容入口。

节点结构为 `{id, question, depends_on, answer_type}`，未知中间答案保留 `${ID.answer}`。Canonicalization 只依据已有字面占位符规范依赖，不能凭声明依赖补造缺失问题语义。未知引用、自依赖、循环和超预算必须失败或在最多一次模型修复后失败。关系 faithful 校验覆盖明确的 birth/death/tenure-end 交换，不代表任意关系语义校验。

PlanValidator 还会剪除满足规则、无后继消费、只计算已有事实的终端比较/计算节点。真正需要外部证据的关系保留；不能写成“比较问题删除最后一节点”。Prompt 本身也禁止纯计算节点，因此这项规则在某些样本上不会改变计划。

### 4.2 DependencyExecutor、AnswerBinder 与 SourceVerifier

按拓扑层执行：将已核验父答案代入问题 → dense retrieval → LLM 引用核验 → 绑定答案和来源。缺少父答案时不猜测答案并搜索后继。默认 `beam_width=1`，只有一个最佳绑定分支，不是多分支推理搜索。

每次依赖 DPR 最多取 Top20；verifier 只看到 Top3，每篇截断 4000 字符。硬检查包括已知 doc ID、原文逐字引用、归一化答案出现在引文内、合法答案形态和最低置信度 0.25；最多一次修复。逐字引用并不保证关系蕴含，LLM 仍可能判断错误。

Pack 收集 proof 时才进一步检查受支持语法中的实体身份、类型与关系主体；未知关系保守弃用。共享候选同时包括初始 base、QD/PCQD 和绑定 DPR 来源，只有一部分有 verified proof。子目标得分还包含与当前 binding requirements 相符的检索分数，因此不能把全部 relation support 解释成已证明关系。

## 5. Pack：联合前缀与有限祖先闭合

### 5.1 EvidenceScorer、CoverageSelector 与 RedundancyController

先对主排名做 query 内 min-max normalization，再融合 base 和子目标分数。Greedy 的实际边际目标为：

\[
u(d\mid S)=0.4B(d)+0.25R(d)+0.45\Delta C(d\mid S)-0.15Red(d,S).
\]

`R` 是候选目标分数最大值，`ΔC` 是各目标当前最大覆盖的新增量平均，`Red` 是与已选文档归一化词集合的最大 Jaccard。四项不是概率，无需加和为 1。先选至多 5 篇，再接 base/goal 融合分数排序的 tail；不是独立 pointwise Top-K。这一步不强制 DAG 祖先闭包，覆盖也包含静态/PCQD 子目标，不能当作 gold DAG coverage。

### 5.2 DAGPackageSelector

读取预测 plan、获胜 bindings、精确匹配获胜分支和合格来源 proof，枚举有限祖先闭合节点子集及来源组合。同一文档支持多个节点只占一个文档预算。

选择顺序与约束：

1. 优化 Top5，固定前 2 篇，并保护前缀已有合格 proof 来源。
2. 优化 Top10，固定已经得到的前 5 篇。
3. 词典序优先增加闭合终端数，再增加全部闭合节点数，再减少新增文档数与原始排名和。
4. 保持候选全集、Top200 文档集合、Top2 与去重不变量；无严格覆盖改进或校验失败时保留原排名。

不是一般集合目标的全局精确求解。最多处理 6 个 plan 节点、深度 4。只有“本节点有合格来源且祖先已覆盖”的节点计入 closed coverage；未闭合后继文档仍可能留在输出，只是不计闭合贡献。因此可提升包具有闭合约束，不代表返回前缀的所有文档构成纯闭合包。

该步骤没有额外 LLM 或检索请求，受既有候选召回与 proof 覆盖上限约束。闭合针对预测 plan 和本地合格 proof，不是未知 gold DAG。

### 5.3 最终 support guard 与 semantic veto

完整 Pack 最后还包含独立提案与审核。Proposer 最多把原排名 6–10 的一篇与 3–5 的一篇互换，本地来源保护和独立 reviewer 均通过才应用。额外请求至多 0–2 次，保持 Top2、Top10/Top200 集合和第 10 名之后顺序，保护已有支撑来源。它确实会修改结果，不能当作无计算开销的过滤器。

## 6. 四组 BindPack 消融及配置

| 实验 | `stage_ablation` | 严格定义 |
| --- | --- | --- |
| Full BindPack | `full` | 完整 Route + Plan/Bind + greedy/DAG Pack + final safeguard |
| w/o Route | `wo_route` | fact-frequency seeds + DPR restart + 固定 damping 的基础图检索，删除增强 seeds/IDF、bridge、iterative、QD/PCQD、path-set；保留 Plan 和 Pack |
| w/o Plan | `wo_plan` | 不规划、不执行依赖 DPR、不绑定、不产生 proof，清空 DAG；保留 Route 和 flat coverage/redundancy Pack，DAG package 因无输入跳过 |
| w/o Pack | `wo_pack` | 保留相同 Route/Plan 候选与状态，仅按原 base/goal pointwise 分数排序；删除 greedy、DAG package 与 final safeguard |

`wo_route` 使用本项目公共索引与 fact filter，是固定的基础候选适配器，不代表独立外部 HippoRAG2 benchmark。`wo_plan` 保留 final safeguard，但没有 Plan proof 保护；不能写作完整 DAG Pack。`wo_pack` 关闭 safeguard，避免最终集合交换补回被删除的 Pack。

Plan 和 DAG Pack 存在真实依赖，因此四组不是无交互的 `2³` 组合；也不能预设消融分数一定下降。

参数位置明确分工：

| 文件/对象 | 职责 |
| --- | --- |
| `src/bindpack/configuration/defaults.json` | 算法默认数值唯一来源：`runtime/candidates/route/plan/pack` |
| `src/bindpack/configuration/*.py` | 分阶段类型、范围与结构校验，不再复制一份数值 |
| `src/bindpack/config.py` | 组合 `BindPackConfig`，读取方法文件与四组模式校验 |
| `configs/ablations_qwen3.json` | 数据/模型资源、服务、Python、输出、采样与评测编排；引用方法文件 |
| `cfg.candidates/.route/.plan/.pack` | 运行时使用的嵌套配置对象 |

```python
from bindpack import BindPack, BindPackConfig

cfg = BindPackConfig.from_file(
    "src/bindpack/configuration/defaults.json",
    stage_ablation="full",
    save_dir="outputs/my_full/index",
)
rag = BindPack(config=cfg)
```

配置优先级为：命令行资源覆盖 > `configs/ablations_qwen3.json` 的 runtime/evaluation 设置 > 引用的方法文件 > 包内默认方法参数。`route/plan/pack/candidates` 的固定算法数值只由方法 JSON 提供，runner 不再提供历史 flags 或局部算法 CLI。模型地址、批大小等 runtime 资源可被实验配置覆盖，这是有意的资源覆盖，不表示每个 runtime 值只能出现在一份文件中。

默认 LLM 为 Qwen3-8B（服务 ID `qwen3-8b`），embedding 为 Qwen3-Embedding-8B。切换 embedding 必须建立新索引，不能因维度相同复用 NV-Embed-v2 向量空间。

四组统一入口：

```bash
bash scripts/run_bindpack_ablations_qwen3.sh --dry-run
bash scripts/run_bindpack_ablations_qwen3.sh --smoke --datasets hotpotqa --sample-size 1
bash scripts/run_bindpack_ablations_qwen3.sh
# 复用已核验的 10_5 Qwen 索引，默认四组 BindPack + 外部 HippoRAG 2，含 QA
bash scripts/run_bindpack_four_cases_reuse.sh --dry-run
bash scripts/run_bindpack_four_cases_reuse.sh
```

新建索引与复用索引使用相同四组 BindPack 定义；复用 Shell 另外默认调用仓库外的 `/root/baseline/HippoRAG/main.py`，结果放在独立的 `hippporag2_reproduce` 目录。这是额外方法基线，不是第五个 `stage_ablation` 值。复用入口只读取经过模型/语料/来源核验的已有 Qwen 索引，结果与协议另存，不覆盖历史产物。详细服务、参数快照与断点规则见 [四组运行说明](四组实验-Qwen3.md)。不再维护旧 NV2 文件名或细粒度组件实验入口。

## 7. 公平协议与指标边界

四组固定相同 corpus、split、sample IDs、embedding、OpenIE/index、reader、prompt、K 与上下文 token 截断。共享索引一次构建后复制独立可写副本，每组 LLM cache 独立；数据、方法参数快照、模型配置和代码哈希写入协议，resume 不允许漂移。

检索候选预算 20、共享池 80、依赖搜索预算 20、Pack 前缀 5、最终返回 200、展示 10、reader Top5 是不同概念。新建索引 Shell 默认 `retrieve`，只生成检索指标；复用 Shell 默认 `rag_qa`，实际运行 reader 并生成 QA EM/F1。外部 HippoRAG 2 使用自身检索与 reader 实现，其输入限制、代码版本范围见运行说明。

| 指标 | 当前意义 | 边界 |
| --- | --- | --- |
| Recall@K | 按完整 passage 字符串匹配 gold，逐 query 宏平均 | 需要统一分块和 passage identity，不是标题 recall |
| FCR@5/10 | 非空 gold 样本 `all_gold_in_top5/10` 平均 | 全部 gold 同时出现，不等于依赖绑定正确 |
| EM/F1 | 实际 reader 输出的 QA 指标 | 必须使用同一 reader 协议 |
| predicted-plan closed coverage | DAG trace 的闭合节点/终端覆盖 | 机制诊断，不能重命名为 gold-DAG DCC |
| DCC/gold-DAG 指标 | 尚无统一 evaluator 实现 | 不能用各方法自己的预测 plan 当作共同 gold 分母 |

Hop 必须显式提供 1–4：MuSiQue 使用 decomposition 长度的 per-question oracle，HotpotQA/2Wiki 使用固定 2-hop dataset prior。样本 manifest 记录来源，不能写成在线自动预测 hop，也不能把 hop 元数据和读取 gold 答案/支撑文档混为一谈。

效果分析可以报告 hop 分层、Top5/10 promotion、proof 接受/拒绝、计划有效率、缺父节点率、LLM calls/tokens/延迟及成对置信区间。冻结同一候选和 Plan state 比较 Pack 能隔离重排影响；Plan/Route 真实重跑会改变下游候选，不能用旧排名伪造。

重构验证应在相同模型、索引、样本与缓存响应下比较 Full 的候选、顺序、分数、prompt 和 trace。CPU 测试、小样本 GPU 或历史冻结回放都不等于全量 benchmark 提升；模型切换本身也不能用源码等价性担保分数不变。实际执行范围和结果以本轮验证报告为准。
